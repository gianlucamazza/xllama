## Reproduce and interpret the ledger

`github-snapshot.ndjson` contains one JSON object per public issue, PR, branch, tag, release, milestone and discussion returned by the APIs, plus workflows for main and the thirteen PRs above. The catalogue was fetched over November 28, 11:24–11:25 UTC. The mutable first page, branch list, main ref and milestones were read again around 11:25:46–49 UTC. Workflow observations can be later; every workflow row carries its own timestamp. The issues collection took eight pages; the PR collection took six. Lower-numbered history came from the initial pagination. GitHub has no atomic transaction across these APIs. Private or deleted objects are outside this inventory.

`mentions`, `mentions_issues` and `mentioned_by_pr` are numbers written in descriptions, which may include historical references. A structural parent is recorded only when the GitHub sub-issue endpoint returned it. Checklist counts reflect the description at capture; the per-issue `next_acceptance` is an audit action. Merge SHAs, Actions IDs, direct links and the release asset digests provide separate evidence. A closed issue with unchecked items requires its original evidence before claiming acceptance.

```sh
jq -c 'select(.type == "issue" and .state == "open") | {number,milestone,next_acceptance,url}' github-snapshot.ndjson
jq -c 'select(.type == "branch") | {name,head_sha,ahead,behind,open_prs}' github-snapshot.ndjson
jq -c 'select(.type == "workflow") | {head_sha,name,conclusion,html_url}' github-snapshot.ndjson
```

For a live comparison, enumerate from the same endpoints with GitHub's `rel="next"` links until exhaustion. With the downloaded public release files, run `sha256sum -c SHA256SUMS` in the asset directory, inspect `unzip -p xllama_1.11.0.2203_x64.msix AppxManifest.xml`, and hash the embedded DLLs against the release tag's vendor records. See the [release policy](../../../release-readiness.md) and [physical validation procedure](../../../console-validation-runbook.md).
