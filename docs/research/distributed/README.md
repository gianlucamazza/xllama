# Distributed inference on consumer Xbox consoles

**DC-0 research.** A PC can assign independent requests to existing foreground xllama servers. The first useful experiment is to measure whether two Series S replicas improve completed throughput at a fixed quality and latency target. A single larger model requires a different mechanism: layer placement with bounded memory and measured transfers on every participating device. Multi-console inference has no Xbox acceptance receipt. [Tracking issue #687](https://github.com/gianlucamazza/xllama/issues/687) · [OOC-6 in #536](https://github.com/gianlucamazza/xllama/issues/536).

## Decision at this checkpoint

**Proposed go** for an operator-reviewed two-console network and budget survey, followed by a host-coordinated HTTP replica trial if DC-1 passes. Include a PC-only baseline on that same hardware. **Hold** the two-node single-model device experiment. Its prerequisites are a viable UWP worker, controllable failure behavior, verified tensor/KV placement, per-rank peak memory and an independently runnable numerical reference. An Xbox coordinator or distributed SSD-backed experts would need additional evidence.

| Research question                                        | Evidence and condition                                                                                                                                                                                                                                                                                                                                                                                              |
| -------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| One service, more simultaneous requests?                 | **Proposed.** One external client can select among opt-in replicas using the existing per-console HTTP surface. Each worker must fit the full model. Compare admission, throughput and tail latency under concurrent demand.                                                                                                                                                                                        |
| One model above one console's memory budget?             | **Estimated.** Whole-layer sharding can fit some synthetic profiles on multiple workers. Each process must fit its largest stage, KV, temporary buffers and load peak. The coordinator also needs file and staging headroom. Current GGML/UWP integration is **Unverified**.                                                                                                                                        |
| Faster response for a single user?                       | **Unverified.** Sequential decode waits for all participating stages. A new boundary adds relay, copy and synchronization costs. Report any queueing benefit under load separately from isolated token latency.                                                                                                                                                                                                     |
| Expert parallelism or edge SSD?                          | **Proposed.** Selected-expert ownership could reduce local weight residency. Network locality, imbalance, cold SSD reads and weighted reduction can dominate. Measure all four with the original router.                                                                                                                                                                                                            |
| Heterogeneous S/X/PC, or an Xbox coordinating by itself? | **Proposed.** Weight allocation must follow stage time, capacity and operator coverage. An Xbox coordinator additionally needs budget for local work and staging plus a tested foreground and recovery lifecycle.                                                                                                                                                                                                   |
| Economically competitive?                                | **Unverified.** Compare owned and newly acquired equipment against a single PC at the same quality, throughput and latency target. The model prices equipment, utilization, wall energy, coordinator and switch. Changing any of these can change the verdict.                                                                                                                                                      |
| A DGX Spark-style cable chain?                           | **Rejected as a design assumption.** NVIDIA documents explicit ConnectX-7 networking and software. Each console exposes one nominal gigabit Ethernet interface; the proposed physical topology is a switched LAN. The logical pipeline can cross the PC twice at a single layer boundary. [DGX Spark clustering](https://docs.nvidia.com/dgx/dgx-spark/spark-clustering.html) · [Xbox and PC evidence](platform.md) |

**Evidence labels.** **Verified** means supported by source, specification or repository metadata at the cited revision. **Measured** requires a named machine, method and scope; earlier single-device measurements and host tests retain their original scope. **Estimated** identifies calculations from stated inputs. **Proposed** identifies a design or decision for review. **Unverified** identifies a claim missing the necessary evidence. **Rejected** identifies a specific assumption or candidate that failed its stated test, conflicts with a documented capability, or was ruled out for a particular stage for a stated reason. A single row can contain more than one kind of evidence.
