## What the shipping build contains

**Verified.** Linux xllama builds the patched submodule, enables upstream tools and disables the upstream HTTP server and upstream tests. GGML's RPC option defaults to off. The shipping UWP project explicitly compiles GGML CPU sources, defines `GGML_USE_CPU` and `GGML_USE_CPU_REPACK`, and omits the RPC sources and definition. The patch ledger at this xllama commit has six active patches (0001, 0003–0007). Patch 0001 covers AppContainer imports. The other five concern K-shift, recurrent state or tool parsing. None wires RPC into the package. The repository's older four-patch audit predates the final two parser backports. [Host build][xhost] · [RPC build switch][pin-option] · [UWP GGML project][xuwp] · [active patch ledger][xpatch]

**Verified.** The xllama GGUF layer helper explicitly selects a local D3D12 device or an empty accelerator list, and sets `offload_kqv = false` when GPU layers are used. The local backend has selective operator and format support. ONNX Runtime GenAI/DirectML is a separate inference path. Running an upstream desktop binary with `--rpc` does not exercise either xllama backend on Xbox. [xllama placement policy][xpolicy] · [runtime routing and D3D12 coverage][xarch]

| Registration and discovery | The registry adds RPC only when built in or loaded. Upstream's `--rpc` registers specified endpoints via `ggml_backend_rpc_add_server`, enumerates device count and creates `RPC0`, `RPC1`, etc. The worker normally exposes accelerators and falls back to CPU. [Registry][registry] · [client][reg-client] · [worker][worker-devices]                                                                                                                                          | Record the real backend and hardware on each worker. The proxy reports GPU type even for a CPU worker, and its `supports_op` returns true without a remote query. Enumeration does not establish operator coverage. [Proxy properties][proxy]                                                                                                                                        |
| Resource ownership         | Allocation, size/alignment queries, buffer/tensor set/get, same-server copy, graph compute/recompute and free are remote operations. A graph is serialized when its UID cannot be reused. Worker buffers are scoped to a connection. [Command list][cmds] · [graph][graph] · [connection cleanup][cleanup]                                                                                                                                                                       | The coordinator owns model loading, scheduling and sampling. Workers own their assigned allocations, graph state and compute. Record graph submissions, tensor payloads and copies separately. If the caller explicitly starts a new request, replay the original token prefix with a full prefill. A lost shard invalidates its KV. Report any output already delivered as partial. |
| Placement and KV           | Default layer split uses reported free memory or explicit proportions, assigns contiguous repeating layers and normally keeps the input layer on the host. With KV offload enabled, a standard per-layer KV cache chooses the layer's device, otherwise CPU. Output layers, tied weights, hybrid/recurrent architectures and scheduler fallback require separate accounting. [Placement][placement] · [KV][kv]                                                                   | Record actual weight, KV and compute-buffer placement by layer. The CPU worker reports physical memory on Windows and treats all physical pages as free on the inspected POSIX branch. Use xllama's app and DXGI readings for admission, with headroom. [CPU memory][cpumem] · [Xbox probes][xbudget]                                                                                |
| Worker-to-worker traffic   | The pin's dispatchers refuse a direct buffer copy between distinct servers. The generic fallback synchronizes the backends, gets the bytes into host memory and sets the destination. [RPC copy][copy] · [GGML fallback][fallback]                                                                                                                                                                                                                                               | For two remote workers, budget **two network legs and a coordinator staging allocation** per such boundary. A local-to-remote boundary needs one network leg. Logits, input, graph metadata and repeated scheduler splits can add traffic. A direct ring/boundary bandwidth formula is an alternative lower bound.                                                                   |
| Cache and storage          | An optional worker disk cache can avoid re-uploading weight transfers **larger than 10 MiB**. The client checks weight buffer usage, and the lookup uses FNV-1a. It does not implement a routed expert cache or migrate KV. [Weight cache][cache] · [threshold and commands][cmds]                                                                                                                                                                                               | Compare cold and warm load separately. Use a cryptographic digest for the model and shard manifest, disable the cache in the first test, then qualify quota, eviction and cleanup before enabling it.                                                                                                                                                                                |
| Tensor splitting and scale | `--tensor-split` also distributes layer proportions. A tensor-split option alone does not prove per-layer distributed tensor parallelism. The pin has layer/row/tensor modes, architecture checks, a declared 16-server value, and `llama_max_devices() == 16`. Its CLI rejects **16 or more** explicit ratios. The examined upstream accepts 16 and rejects more. [Split modes][split] · [device count][max-dev] · [pin parser][pin-split-arg] · [current parser][up-split-arg] | Use two explicit CPU workers and inspect layer logs. Treat 16 as boundary-condition research and 32 sharded devices as analytical extrapolation. Independent request replicas have a different limit.                                                                                                                                                                                |
| Networking and lifecycle   | The pin's Windows transport links Winsock, uses IPv4 TCP with blocking reads and writes, and disables RDMA on Windows. The server synchronously serves one connected client at a time. Its public server-start call has no stop handle. A failed connection/handshake or midstream I/O can abort the pin's client. [Transport][transport] · [build dependencies][deps] · [server loop][loop] · [connection failure][fatal]                                                       | Run initial host spikes in disposable processes with a supervisor deadline. Require a UWP import audit, package-local storage, private-network capability, suspend/resume and cancellation evidence. A supported desktop Winsock call alone gives no package qualification. [Winsock API requirements][winsock]                                                                      |

**Verified scheduler condition.** A model can span devices while each token still executes its layer groups in sequence. In the pin, the optional pipeline scheduler additionally requires more than one model device, full layer offload including output, layer split mode, K/Q/V offload, no tensor overrides and async/event support on the relevant non-CPU backends. It can fall back when the larger compute allocation fails. The existing local D3D12 policy disables K/Q/V offload. Record the scheduler's actual enable/fallback log and overlap before applying an ideal microbatch-throughput estimate. ## Host observation

**Measured.** On the candidate base, the prepared pin's upstream `test-rpc-multi-server` passed **1/1** on Linux x86-64 (Release, GCC 14.2.0, CMake/CTest 3.31.10). One native test client used two independent CPU worker processes on the same host. Both bound exclusively to `127.0.0.1` over TCP. The test took **0.07 s wall clock** including the fixture. It checked remote allocation, graph submission and distinct allocation sizes for two tensor layouts. It loaded no model. No Xbox, LAN, distributed logits, failure recovery or performance measurement follows from this run. [Commands, patch identities, participant roles and results](evidence/host-rpc.json)

### DC-3 matched CPU arithmetic on Linux, 2026-11-28

**MEASURED.** At xllama `e2abab1f4510ca8cc96fa47f378bc00f7b4bc7e8`, the prepared v0.6.0 gitlink and the pristine upstream [v1.1.0 release](https://github.com/ggml-org/llama.cpp/tree/171527522610996f5f0acf12334e185156ca8f44) each ran with matching client and workers. One F32 ADD graph ran on the first loopback CPU worker, `ggml_backend_tensor_copy` moved its four-element result to the second, and a second ADD ran there. Local control, worker pair, fresh local process after worker shutdown and a restarted pair all produced `[5, 0, 0, 25]` in each lane. Each backend reported a 96-byte tensor allocation. The logical boundary held 16 bytes. Process high-water memory and on-wire byte counts remain unmeasured. The stock two-worker CTest also passed for each revision. The [fixture](evidence/rpc-add.cpp) and [receipt](evidence/host-rpc-add.json) give the graph, CPU worker endpoints, source and binary hashes, and raw results.

To replay on Linux, prepare the repository's pin with the patch script above and a second, pristine checkout of the recorded v1.1.0 SHA. From the xllama repository root, run the following once per lane with `src` pointing to the chosen llama.cpp source tree and `build` pointing to a different empty build directory for each tree. The upstream harness launches both workers on loopback and cleans them up on exit.

```sh
cmake -S "$src" -B "$build" -G Ninja -DCMAKE_BUILD_TYPE=Release \
  -DBUILD_SHARED_LIBS=OFF -DGGML_NATIVE=OFF -DGGML_RPC=ON -DGGML_RPC_RDMA=OFF \
  -DGGML_BACKEND_DL=OFF -DLLAMA_BUILD_COMMON=ON -DLLAMA_BUILD_TESTS=ON \
  -DLLAMA_BUILD_TOOLS=ON -DLLAMA_BUILD_SERVER=OFF -DLLAMA_BUILD_EXAMPLES=OFF -DLLAMA_OPENSSL=OFF
cmake --build "$build" --target ggml-rpc-server test-rpc-multi-server --parallel 2
ctest --test-dir "$build" -R '^test-rpc-multi-server$' --timeout 30 --output-on-failure --no-tests=error
g++ -std=c++17 -O2 -Wall -Wextra -Werror -I"$src/ggml/include" \
  docs/research/distributed/evidence/rpc-add.cpp -L"$build/ggml/src" \
  -L"$build/ggml/src/ggml-rpc" -lggml -lggml-cpu -lggml-rpc -lggml-base \
  -fopenmp -lpthread -ldl -o "$build/bin/rpc-add"
timeout 30 "$build/bin/rpc-add"
timeout 30 bash "$src/tests/test-rpc-multi-server.sh" "$build/bin/ggml-rpc-server" "$build/bin/rpc-add"
timeout 30 "$build/bin/rpc-add"
timeout 30 bash "$src/tests/test-rpc-multi-server.sh" "$build/bin/ggml-rpc-server" "$build/bin/rpc-add"
```

## Minimum reuse experiment

**Proposed.** Retain the stock data plane and the local-only default. Compare two separately identified CPU lanes. Lane P is xllama's prepared pin. Lane U is pristine upstream at the recorded SHA. Obtain a passing matched pair within each lane. Keep production pin changes under the independent [#522 gate][pin-gate].

1. Record both commits, patch hashes, compiler, architecture and CMake cache. In a disposable checkout of xllama, run `scripts/apply-llama-patches.sh` and its `--check` mode. Configure upstream as a **standalone** build against this prepared submodule so its test switch is effective. Enable `GGML_RPC` and `LLAMA_BUILD_TESTS`, with `GGML_BACKEND_DL=OFF` and `GGML_RPC_RDMA=OFF`. Use the binary names from that revision. The pinned Unix CTest `test-rpc-multi-server` already exercises two loopback CPU workers, buffer ownership and allocation sizing. Its scope ends before model inference. [Pinned CTest registration][ctest] · [test fixture][fixture]
2. In the proposed DC-3/DC-4 sequence, use an identified, locally available small GGUF. Compare a CPU reference and a fixed two-worker layer split with the same tokens and context. Capture device identities, per-layer split, actual ports/transport, prefill/decode traffic, coordinator/worker peak memory and raw aligned logits. Treat built-in device type/operation flags as insufficient. The first model test requires placement and parity evidence together.
3. Reuse upstream CLI, CTest and worker entry points before considering a UWP adapter. Prefer an upstreamable change for clean stop, resource limits or API-family portability if such a change is required. A minimal opt-in UWP worker would still need a package build/import audit and bounded teardown on suspend. No pin upgrade, new protocol, listener or D3D12 route is proposed for the shipping app here.

**Unverified.** The source comparison establishes no Xbox RPC compatibility, console-to-console throughput, distributed GPU support, model-size increase or safe process recovery. Those observations require separately approved hardware runs. Any previously collected single-node GPU or MoE receipt stays attributable to its original package.
