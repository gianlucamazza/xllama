# Xbox resources and the DC-1 network experiment

**Decision pending.** The first question is whether the _application on the two intended consoles_ can sustain the message sizes and deadlines the proposed split requires. Existing Series S and independent Series X runs cover a single console at a time. Their client-visible timings include inference and HTTP handling. There are no multi-console measurements in this study.

Application placement checks:

- **Verified.** Microsoft distinguishes the foreground CPU and GPU shares of an App from the allocation for a Game. Its UWP resource page applies to Series X and S, requires x64, and documents a debugger exception to the memory limit. Run a packaged release with the debugger detached. xLlama's x64 manifest targets both Windows.Xbox and Windows.Desktop. A desktop build passing establishes only that desktop configuration. [Microsoft resource allocation](https://learn.microsoft.com/en-us/previous-versions/windows/uwp/xbox-apps/system-resource-allocation) · [xLlama manifest](../../../uwp/AppxManifest.xml)
- **Measured (prior, single node).** The project records the Series S Game DXGI LOCAL budget and an example where model load succeeded but the inference working set exceeded budget. CPU core count alone also failed to distinguish App from Game in the independent Series X trial. Record `[resources]`, phase working set, `gpu_mem_mb` and `gpu_budget_mb` per process. Windows can increase the initial limit after Xbox launches. An additional probe could sample `AppMemoryUsage`, `AppMemoryUsageLimit` and limit-change notifications over the run. The published “mb” code divides by 2²⁰. [Platform probe](../../../src/bridge/platform.cpp) · [platform evidence §§5, 7, 11](../../uwp-constraints.md) · [expected memory limit](https://learn.microsoft.com/en-us/uwp/api/windows.system.memorymanager.expectedappmemoryusagelimit) · [DXGI budget and usage](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_4/nf-dxgi1_4-idxgiadapter3-queryvideomemoryinfo)
- **Rejected as a sizing assumption.** Adding the GPU budget to the process cap double-counts shared memory. Summing physical memory across consoles also omits per-node reservations, KV, scratch, staging, copies, tensor alignment and indivisible allocations. Check the peak of every worker and the coordinator, including the load phase. The process may need full checkpoint metadata, temporary weights or repacking even when its steady-state shard fits. The pinned GGML CPU device reports system physical memory on Windows; an RPC free-memory response cannot replace the Xbox process/DXGI readings. Only an allocation trace settles peak use. [Pinned CPU device query](https://github.com/ggml-org/llama.cpp/blob/d81235049384534c167caea52b85a694f6103d14/ggml/src/ggml-cpu/ggml-cpu.cpp#L365-L380)
- **Measured (prior, single node).** xLlama measured LocalState free space on its own volume. The Dev Home allocation and nominal size of the internal SSD give different quantities. Recheck the writable volume, free space and file visibility from the app. Existing USB provisioning paths do not establish SSD-backed expert-read performance. Measure internal, expansion and USB paths separately if accessible, using identical files, cold/warm conditions, read sizes and queue depths. A logical read counter or a Windows cache hit cannot establish physical SSD traffic. [Constraints §§2, 8, 9](../../uwp-constraints.md) · [provisioning](../../model-selection.md)
- **Verified.** The manifest declares `internetClient` and `privateNetworkClientServer`. The shipped optional HTTP listener uses WinRT `StreamSocketListener` on an operator-selected LAN port; it exposes `/health` and `/v1/models` and shares one resident session with the UI. The endpoint is unauthenticated. The Microsoft API describes TCP client/server support, network isolation and restricted same-machine communication; a same-host loopback check cannot qualify console-to-console traffic. The built-in WinRT TLS facility on `StreamSocket` is client-side. Server authentication/encryption for a future worker needs a separately demonstrated mechanism. [Endpoint contract](../../api-endpoint.md) · [listener implementation](../../../uwp/api-server.cpp) · [Microsoft sockets](https://learn.microsoft.com/en-us/windows/apps/develop/networking/sockets) · [network capability scope](https://learn.microsoft.com/en-us/windows/apps/develop/networking/networking-basics) · [WinRT listener protection levels](https://learn.microsoft.com/en-us/uwp/api/windows.networking.sockets.streamsocketlistener)
- **Verified documented / Proposed handling.** A UWP game can suspend or terminate when backgrounded. Operate foreground-only. A coordinator must detect liveness loss by deadline, invalidate the affected session, and accept a returning worker only after a fresh capability/budget and artifact check. A suspended worker cannot promise that a cancellation callback will run. A network broker is not evidence of continued inference in the background. [UWP lifecycle](https://learn.microsoft.com/en-us/windows/uwp/launch-resume/app-lifecycle) · [suspend handling](https://learn.microsoft.com/en-us/windows/uwp/launch-resume/suspend-an-app)

## DC-1 procedure for a community tester

**Proposed.** This is an owner-gated experiment. Use two consenting, foreground Developer Mode consoles and an operator-controlled PC on a dedicated trusted LAN. Start with one wired non-blocking switch. A pipeline or logical ring can use that switch. No experiment requires consoles to bridge traffic, a daisy chain, RDMA, GPUDirect, NVLink or wireless mesh. Disable the opt-in listener afterwards.

1. **Identify the devices.** Assign anonymous labels A/B/C. Record hardware SKU, OS build, xLlama commit, submodule commit, MSIX SHA-256 and exact installed package full name, designation, backend, network medium, switch/NIC link speed, port and MTU. Record Dev Home values and the package's measured memory limit after startup. For a model run include GGUF SHA-256, tokenizer, context, thread count, seed and foreground uptime. Wait at least 30 s after launch before the steady-state group. Record cold-start results separately. [Console validation runbook](../../console-validation-runbook.md) · [designation experiment](https://github.com/gianlucamazza/xllama/issues/457)
2. **Check the existing service from the PC.** Opt in through Settings → LAN API on each Xbox. Read its `/health` and `/v1/models`, recording HTTP status, package version, API contract, capabilities and a common installed model. The existing `scripts/validate-api.sh spike` and `discovery` gates also restart the selected app; isolate those runs from latency measurements. The [previous Series S device record](../../../bench/results/2026-09-28-console-api-validation.json) contains protocol results. For application timing the [existing client](../../../scripts/measure-api-ttfb.py) records connect, headers, first body byte, first content delta and completion. Label these HTTP/inference observations. A health response from both devices leaves the peer-to-peer data path untested.
3. **Calibrate the network.** First, where two PCs are available, run a single-stream [iperf3](https://software.es.net/iperf/invoking.html) baseline in both directions on the same switch, port/cable class and MTU. Label it PC↔PC. Then use an approved, bounded, foreground UWP bench build or validated port of an existing tool to transfer known bytes ending at the Xbox process. This study supplies no console probe. Prefer standard TCP/HTTP fixed-length upload, download and echo; verify payload length and digest. Keep fixed preallocated buffers and an explicit declared total size. Host-side packet capture or switch counters can corroborate traffic on the operator-controlled pair. Record pre/post counter deltas and competing traffic.
4. **Run the message-size sweep.** Reuse an established connection for steady-state RTT. Time a small request and matching reply on the initiating process's monotonic clock; record connection setup separately. Sweep 64 B, 4 KiB, 16 KiB, 256 KiB and 1 MiB to bracket scalar RPCs, token activations and prefill blocks. For sustained transfer run 30 s after a 5 s warm-up, three repetitions in each direction, then simultaneously both ways and with shared uplinks. Record receiver-verified payload bytes per elapsed second, latency P50/P95/P99 and max, sample count, failure/timeouts and per-direction results. Target at least 1,000 short-message samples per size for tail analysis; flag smaller samples as exploratory. Capture Wi-Fi in a distinct group with band/channel and interference observations. Do not halve RTT into measured one-way latency.
5. **Attribute the overhead.** On the future probe, time host buffer preparation, serialize/deserialize, queue wait, write/read completion and backend upload/readback/fence separately, each with local monotonic timestamps. A socket write completing measures an API boundary; verify receipt on the peer. Match a CPU-to-CPU copy-only control with a GPU-resident → staging → socket → staging → GPU trial where the backend supports it. Include bytes for both directions, per-message metadata, actual activation dtype and stride, and the process/GPU high-water values. A single PC with a fast GPU provides a useful control for staging, never an Xbox result.
6. **Exercise the failure cases.** For one bounded request, use an operator-driven suspend/resume, then a separate clean disconnect/reconnect. Record last progress, deadline, result/partial-output disposition, ownership of permits/buffers and fresh-session readiness after the worker returns. Run the existing single-node path with the distributed bench inactive to verify recovery. Stop on unexpected memory growth, a stuck worker, unexplained bytes, or an inability to close the listener. Keep failed runs, prefix partial output, and publish anonymized logs without Device Portal credentials or network identifiers.

Persist one raw row per attempt with run ID, source/destination labels, direction, transport, concurrent streams, payload bytes, sample duration, application/wire bytes (each explicitly sourced), duration units, warm-up, error, memory, GPU and package metadata. Use `null` for unavailable counters. Repeat with PC→A, PC→B, A→B and B→A; only the last two qualify a direct console edge. A coordinator-staged A→PC→B path is a separate measurement with two transfers.

**Estimated lower bound.** On a 1 Gb/s link, 125,000,000 B/s is the best possible raw line rate per direction. A 16 KiB payload alone therefore costs at least 0.131072 ms to serialize onto one link. TCP goodput, request/reply dependency, queueing, host serialization and GPU staging add time. For sequential messages of payload size `S` and `n` exchanges on the measured path, budget `n × (fixed exchange time + total payload bytes per exchange / receiver goodput)`. Use a small-message intercept with consistent directionality or fit latency versus bytes; avoid charging full measured echo RTT twice. If the observed P95 exceeds the communication allowance left after local computation, either change the proposed cut and repeat or stop that strategy. A successful HTTP reachability test can inform the separate request-replica experiment. A single-model trial requires measurements of its actual transfer route under contention and the GGML compatibility gate. For a coordinator relay, measure A→PC→B and the reverse with both hops active. Require direct A↔B receipts only for a design that transfers directly between the consoles.
