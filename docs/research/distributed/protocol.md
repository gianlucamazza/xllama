# Experimental protocol for distributed inference

**Proposed, DC-2 through DC-9.** Each campaign needs its own gate and signed-off declaration. The comparison unit is one complete request with identical semantics, or a fixed arrival trace of such requests. Establish the [network and resource envelope](platform.md) on the path the candidate actually uses and meet the [trust and recovery conditions](security.md). Historical single-console results can identify test cases; produce new matched reference rows for any speed or cost claim.

Separately measure multi-stream pipeline throughput and overlap. Include load-time coordinator peak and actual direct or relayed traffic. |
| Series X with S and/or PC                                                                   | Measure each participant alone, then compare balanced and capability-weighted placement on the same devices. Record which stages the PC computes.                                                                                                                                                                                  | Heterogeneous placement, slowest stage, memory bottleneck and sensitivity to one missing worker.                                                                              |
| Resident, single-node SSD-backed, distributed resident experts, then distributed SSD-backed | Once the respective gates open, pair each arm with the same GGUF, original router, prompt IDs and prompt schedule. Use the same declared byte cap across bounded-cache arms; record the full resident reference footprint. When testing cache or storage policy, change one at a time and record warm and cold results separately. | Isolate offload effects, network dispatch and their interaction. Verify router choices, weighted aggregation, physical reads where available and logical miss traffic.        |

A single-node OOM is a capacity observation. If the reference cannot run, record the preflight refusal and limiting allocation, or the observed failure if an admitted run fails. Mark same-device speedup and efficiency unavailable. For a capacity-only claim demonstrate correct completion and bounded peaks on **every** participant. A smaller or differently quantized model is a separate cost/quality comparison. Missing devices remain **Unverified**.

## Freeze the campaign before the candidate run

- Record source commits, patchset, binary/package/model/tokenizer/template hashes, GGUF tensor layout and quantization, node roles, backend and kernel, OS, App/Game designation, CPU affinity where controllable, thread and batch/microbatch counts, GPU layers, KV types, context and output limit, wire route, power boundary and admission limits. Record actual allocations and applied configuration. Disable unrelated network/SSD load. Change one variable per ablation. [Bench methodology](../../../bench/README.md)
- Freeze prompt/continuation IDs, sampler and per-request seeds (e.g. 42), stop policy, reasoning settings and requested/actual token counts. Use short and long prefill, sustained decode, single-stream and contended independent requests, plus an explicit multi-turn affinity case. Fix the arrival schedule, offered concurrency, retry policy, deadline and queue size. Log planned arrival and actual dispatch to include queue delay. Thermal steady state, representative prompt mix, read/cache state and topology are part of the cell.
- Separate fresh process/model load, warm weights with new KV, prefix reuse, cold/warm expert cache and OS file-cache state. Label OS cache unknown unless explicitly controlled or observed. Within a warm cell drop one named warm-up and keep at least three independent post-equilibrium repetitions, each with its own row. Capture cold trials separately. Alternate baseline/candidate AB then BA with matched prompts and arrival traces. For a performance decision predeclare pair count and confidence level, use paired intervals across independent pairs and report median and spread. A three-run smoke does not qualify a tail-latency claim. [Paired experiment conventions](../../../bench/README.md#xbox-series-s--paired-ab-campaigns)

## Metrics and decision rules

| Measurement              | Definition and acceptance                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TTFT, prefill and decode | Engine TTFT runs from prefill start to first generated token. Client time-to-first-content runs from request start to the first nonempty content delta; queue, connect, headers and first response byte have separate timestamps. A keepalive or empty SSE event cannot establish first content. Prefill rate uses actually evaluated input tokens/prefill time. Record generated IDs and engine decode time; a client inter-token estimate uses `(N−1)/(last−first)` only for at least two timestamped tokens. An SSE frame may contain multiple tokens. [Existing client](../../../scripts/measure-api-ttfb.py)                                                                            |
| End-to-end and aggregate | End-to-end runs from planned arrival to terminal success/error. In a fixed, declared window, count only successful, semantically accepted output tokens divided by elapsed campaign wall time; include idle, queue and drain according to the frozen boundary. Report successful requests/s, total offered, admitted, success, timeout, cancellation, partial, retries and HTTP 503 counts. Separate error latency and success-only P50/P95/P99; record denominator and percentile method, and interval by independent block. Collect at least 1,000 requests per cell before interpreting P99, otherwise label exploratory.                                                                 |
| Scaling                  | For comparable homogeneous runs use aggregate goodput ratio `G_N/G_1`, efficiency `G_N/(N G_1)`. For heterogeneous replicas use `G_mix/Σ G_i` against independently saturated constituent rates. Report single-stream latency ratios separately. A throughput improvement requires the predeclared 95% lower confidence bound above 1 at the declared latency/error budget. A claim of reduced P95 requires the corresponding upper latency-ratio bound below 1 at matched offered load. Crossing a margin is inconclusive.                                                                                                                                                                  |
| Memory and traffic       | Per process record working set and high-water, app usage/limit, DXGI LOCAL usage/budget, staging and temporary peak across load, prefill, decode and teardown. Require each measured peak plus the frozen reserve to fit its respective limit. Record NIC TX/RX and application payload bytes; for aggregate traffic count each physical hop once in one direction, with reverse traffic additional. Divide transfers by accepted tokens; separate startup/model transfer from steady-state activation/control traffic. Record logical and device SSD bytes separately, hit/miss counts and read latency. Unavailable counters stay null.                                                    |
| Energy and cost          | Meter each console, compute/coordinator PC and attributable network equipment over the same wall-clock window. Integrate watts over seconds for joules. Report total and idle-subtracted energy separately, wall-plug J/accepted token, tariff, currency and price date, and acquisition cost, utilization and lifetime assumptions. Electricity per accepted token is `joules × price_per_kWh / (3,600,000 × accepted_tokens)`. Add amortized ownership for the measured interval for a total-cost comparison. With zero accepted tokens report the failed interval and consumed energy; unit cost is undefined. [Wattmeter and sidecar requirements](../../../bench/README.md#methodology) |

Freeze the memory reserve, maximum error/failure rate, p95 deadline, quality non-inferiority margin and practical throughput or cost target before comparing arms. Passing capacity and parity permits analysis of performance; it does not establish that a deployment meets an economic target.

## Correctness and output quality

1. Create resident reference artifacts on an independently runnable reference. Teacher-force identical token IDs into every arm. Index full vocabulary rows by prompt hash, token prefix and absolute sequence position at end-of-prefill and after selected decode inputs. Include layer boundary and dtype when comparing activations. Before computing errors verify shape, ID order, vocab/tokenizer, hashes, row count and finite values. Independently permuted, omitted, duplicated or corrupted rows must fail the verification harness even when rendered text or top token happens to match. For MoE also compare router top-k IDs, weights/order and weighted result on a trace with local, remote, repeated and evicted experts. [MoE reference and controls](../../../bench/moe-streaming/README.md) · [verifier](../../../scripts/verify-moe-parity.py)
2. For the same-source, same-kernel deterministic CPU arm, require zero numeric difference on the declared full rows and identical greedy IDs under matched settings. Confirm repeatability and provenance before applying this diagnostic. A different CPU ISA/kernel or GPU needs an independently frozen numerical declaration; do not loosen an existing one after observing the candidate. For the GGML GPU control use **amended ADR 0010**: reference each captured weight product against float64 of the dequantized operands (with the arm's own q8_K operand), with declared layer coverage including an all-layer capture. Judge many positions against the two CPU arms' noise floor using prompt-bootstrap KL and top-token agreement. Report maximum error and NMSE as diagnostics. Any uncovered operator, heterogeneous GPU backend or unsupported quant requires separate qualification. [ADR amendment](../../adr/0010-logit-parity-reference-spread.md#amendment-2026-11-15) · [reference and distribution comparator](../../../scripts/control-parity.py)
3. For user-visible quality, run the same frozen task IDs and scoring version, for example the [standard generative subsets](../../../scripts/eval-standard-generative.py). Record raw output, termination reasons, score per item, paired change and uncertainty, including refusals, truncations and failures. Classify output quality separately from numerical parity and speed. When evaluating money or energy per accepted token, apply the same frozen success/quality policy to both arms and report its coverage.

**Community evidence record.** Supply the frozen declaration and hash, node/build/model provenance, per-attempt raw CSV/JSONL, wall/engine timestamp definitions, per-rank resource and traffic logs, power traces and calibration, reference/candidate hashes, verifier result, failure receipts and a replay command. Each receipt names attempt ID, node and phase, last progress, terminal status, partial bytes/tokens, retry disposition, and whether all nodes returned to ready/single-node operation. Keep failed or preflight-refused attempts in the ledger. Use the [CSV validator](../../../scripts/validate-benchmark.py) and [sidecar writer](../../../scripts/write-benchmark-sidecar.py) for their existing formats, attach multi-node fields as separate run artifacts, and redact addresses, credentials and private prompts.
